# ADR-001: 依存性注入 (DI) ライブラリ選定

**状態**: 採用済み

**日付**: 2025-12-14

## 背景 (Context)

このプロジェクトではクリーンアーキテクチャを採用しており、レイヤー間の依存関係を管理するために依存性注入 (DI) パターンを利用します。チームは他のプロジェクトで `google/wire` の使用経験があります。

しかし、`google/wire` は2024年初頭に公式にアーカイブされ、今後のメンテナンス（バグ修正、セキュリティパッチ、新しいGoバージョンへの互換性対応など）は提供されないことが発表されました。そのため、`wire` を使い続けることには長期的なリスクが伴うため、代替となるDIライブラリを選定する必要があります。

## 決定要因 (Decision Drivers)

プロジェクトおよびチームの要件に基づき、ライブラリ選定の基準を以下の通り優先順位付けしました。

1.  **コンパイル時の安全性 (最重要)**: 実行時ではなく、コンパイル時に依存関係の不整合を検出できること。
2.  **学習コストの低さ**: チームの既存の `wire` の知識を活用でき、移行や新規メンバーのオンボーディングが容易であること。
3.  **パフォーマンス**: 実行時のリフレクションによるオーバーヘッドがない、または最小限であること。
4.  **メンテナンスの継続性**: ライブラリが積極的にメンテナンスされており、将来のGoバージョンアップや潜在的な問題に対応できること。
5.  **移行コスト**: `wire` からの移行が現実的かつ低コストであること。

## 検討した選択肢 (Considered Options)

要件（特にコンパイル時の安全性）に基づき、以下の3つの選択肢に絞り込みました。`uber-go/dig` のようなリフレクションベースのライブラリは、主要な要件を満たさないため除外しました。

### 1. `mazrean/kessoku`

`google/wire` からフォークされた、コード生成ベースのDIライブラリ。

-   **利点**:
    -   `wire` とほぼ同じAPIとCLIを提供しており、経験豊富なチームメンバーにとって学習コストがほぼゼロ。
    -   コード生成により、コンパイル時の安全性と高いパフォーマンスを維持。
    -   `wire` からの移行は `go.mod` の書き換えとCLIツールの再インストールが主な作業となり、非常に低コスト。
    -   オリジナルの `wire` にはない機能追加やバグ修正も行われている。
-   **欠点**:
    -   個人によるメンテナンスであるため、コントリビューターが限られる。プロジェクトの長期的な継続性については、コミュニティベースのライブラリほどの保証はない。

### 2. 手動DI (Manual Dependency Injection)

ライブラリを使用せず、`main` 関数や専用のDIパッケージ内で手動で依存関係を構築する。

-   **利点**:
    -   外部ライブラリへの依存がなくなる。
    -   Goの標準言語機能のみで構成され、完全に透過的で追跡しやすい。
    -   最高のパフォーマンスを提供する。
-   **欠点**:
    -   プロジェクトが大規模化するにつれて、依存関係の構築コードが非常に複雑で冗長になる。
    -   `wire` が提供していた自動生成の利便性が失われ、生産性が低下する。
    -   `wire` からの移行コストが非常に高い（すべてのDIコードを書き直す必要がある）。

### 3. `google/wire` (現状維持)

アーカイブされたライブラリを使い続ける。

-   **利点**:
    -   移行コストがゼロ。
-   **欠点**:
    -   **メンテナンスが完全に停止している。** 将来のGoバージョンアップに対する互換性やセキュリティ脆弱性への対応が期待できないという、許容できないビジネスリスクを伴う。
    -   コミュニティからのサポートも先細りになる。

## 決定 (Decision)

**`mazrean/kessoku` を採用します。**

## 根拠 (Rationale)

`mazrean/kessoku` は、`google/wire` の最大の懸念事項である「メンテナンス不足」というリスクに直接対処しつつ、他のすべての主要な要件を満たしているため、最も合理的な選択肢です。

-   最重要要件である「コンパイル時の安全性」を満たしています。
-   チームの既存の `wire` の専門知識を活用でき、低い学習コストと移行コストで生産性を維持できます。
-   手動DIへの移行に伴う高いコストと将来的な煩雑さを回避できます。
-   個人によるメンテナンスという将来性への懸念はありますが、「メンテナンスが確実にない」`wire` のリスクと比較すれば、許容可能なリスクであると判断しました。

## 影響 (Consequences)

### ポジティブな影響
-   `wire` とほぼ同じ開発体験を維持しつつ、メンテナンスされているライブラリに移行できます。
-   移行作業は `go.mod` の修正とCLIツールの再インストールが主となり、非常に低コストで完了する見込みです。

### ネガティブな影響
-   `wire` ほどの大きなコミュニティによるサポートは期待できません。ライブラリの動向を注視する必要があります。
-   （もしあれば）`wire` との微細な非互換性については、移行時にテストを通じて確認する必要があります。
