# ADR-002: DIツールの選定

## 1. 決定日

2025年12月23日

## 2. ステータス

提案 (Proposed)

## 3. 決定の背景

現在、プロジェクトではDIコンテナとして `google/wire` を利用している。しかし、`google/wire` はGoogleによってアーカイブ済みとなっており、今後のアップデートやメンテナンスが見込めない状況である。このため、将来的な技術的負債となるリスクを回避し、プロジェクトの持続可能性と品質を維持・向上させるために、代替となるDIツールの選定が急務となっている。

## 4. 決定事項

DIツールとして `mazrean/kessoku` を採用する。

## 5. 決定理由

プロジェクトの要件と各候補ツールの比較検討の結果、`mazrean/kessoku` が最も適切であると判断した。

### 5.1. 要件への合致

* **コンパイル時DI**: `kessoku`はコード生成ベースのコンパイル時DIであり、リフレクションを使用しない。これにより、依存関係の検証がコンパイル時に行われ、実行時エラーのリスクを低減し、型安全性を確保できるという最重要要件を満たす。
* **パフォーマンス**: 実行時オーバーヘッドはほぼゼロであり、`wire`と比較して同等かそれ以上の起動パフォーマンス（並列初期化機能）が期待できる。
* **学習コスト/移行コスト**: `wire`とAPIの概念が非常に似ているため、既存の`wire`ベースのコードからの移行や、新しい開発者の学習コストが低いと予想される。
* **メンテナンス性**: `wire`がアーカイブ済みであるのに対し、`kessoku`は活発にメンテナンスされている。

### 5.2. 各候補との比較

### 5.3. その他の候補が不採用となった理由

* **`google/wire`**: アーカイブ済みのため、長期的なプロジェクトの継続性を考慮すると不適切。
* **`uber-go/dig` / `uber-go/fx`**: リフレクションベースであるため、「コンパイル時にエラー検出したい」という最重要要件を満たせない。`fx`はライフサイクル管理機能が強力だが、フレームワークへの依存度が高い。
* **手動DI**: 小規模プロジェクトでは有効だが、今後のプロジェクト規模拡大を考慮すると記述量と保守性の面で懸念がある。

## 6. 懸念事項と対応策

`mazrean/kessoku`の唯一の大きな懸念点は、`wire`や`fx`と比較してコミュニティサイズが小さく、採用実績が少ないことである。これに対する対応策は以下の通り。

* **詳細調査**: 導入前に、`kessoku`のGitHubリポジトリにおけるIssue/PRの活動状況、コントリビューターの数、最終コミット日時、ロードマップなどをより詳細に調査し、プロジェクトの安定性を見極める。
* **コードベースの評価**: `kessoku`のコードベースがシンプルで理解しやすいものであれば、必要に応じて自社で一部のメンテナンスやデバッグを行うことを検討する。
* **段階的導入**: 最初は限定的な範囲で導入し、問題がないことを確認しながら徐々に適用範囲を広げる。
* **エスケープハッチ**: 万が一`kessoku`の利用が困難になった場合でも、手動DIへの切り替えパスは比較的容易であるため、リスクは許容範囲内と判断する。

## 7. 決定の結果

`mazrean/kessoku`の導入を進める。
