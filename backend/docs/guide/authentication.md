# 認証機能仕様書

## 1. 概要

本システムは **API キー認証** を採用する。クライアントはあらかじめ API キーを発行し、以後のリクエストで `X-API-Key` ヘッダーにそのキーを付与することで認証済みと見なされる。

JWT やセッションは使用しない。キーはサーバー側でハッシュ化して保持し、平文キーはデータベースに保存しない。

---

## 2. 認証フロー

### 2-1. API キー発行フロー

```
クライアント                    サーバー
    │                              │
    │  POST /v1/api-keys           │
    │  { user_id, name }           │
    │ ────────────────────────>    │
    │                              │  ランダム 32 バイト生成
    │                              │  → hex エンコード
    │                              │  → "todo_" プレフィックス付与
    │                              │  → SHA-256 ハッシュを DB 保存
    │                              │
    │  { id, key, user_id, name }  │
    │  <────────────────────────── │
    │                              │
  ※ key（平文）は この1回限り返却
  ※ クライアント側で安全に保管する責務がある
```

### 2-2. リクエスト認証フロー

```
クライアント                    ミドルウェア              DB / キャッシュ
    │                              │                          │
    │  Any Request                 │                          │
    │  X-API-Key: todo_xxxx        │                          │
    │ ────────────────────────>    │                          │
    │                              │  キャッシュ確認           │
    │                              │ ─────────────────────>   │
    │                              │                          │
    │                [HIT]         │  APIKey エンティティ返却   │
    │                              │ <─────────────────────   │
    │                              │                          │
    │                [MISS]        │  SHA-256 ハッシュ化        │
    │                              │  FindByKeyHash(hash)     │
    │                              │ ─────────────────────>   │
    │                              │  APIKey 返却              │
    │                              │ <─────────────────────   │
    │                              │  キャッシュに保存          │
    │                              │ ─────────────────────>   │
    │                              │                          │
    │                              │  ctx に user_id をセット  │
    │                              │  Next()                  │
    │  レスポンス                   │                          │
    │  <────────────────────────── │                          │
```

認証失敗時（キーが存在しない・ヘッダー未設定）は **401 Unauthorized** を返し、処理を中断する。

## 3. エンドポイント仕様

### 3-1. API キー発行

| 項目 | 値 |
|---|---|
| メソッド | `POST` |
| パス | `/v1/api-keys` |
| 認証 | 不要 |

**リクエストボディ**

```json
{
  "user_id": "string (UUID, required)",
  "name": "string (1〜50文字, required)"
}
```

**レスポンス: 201 Created**

```json
{
  "id": "UUID",
  "key": "todo_xxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxx",
  "user_id": "UUID",
  "name": "string",
  "created_at": "RFC3339"
}
```

> `key` フィールドはこのレスポンスでのみ返却される。再取得は不可。

**エラーレスポンス**

| ステータス | 条件 |
|---|---|
| 400 Bad Request | バリデーションエラー（必須項目欠損、形式不正） |

---

### 3-2. API キー削除

| 項目 | 値 |
|---|---|
| メソッド | `DELETE` |
| パス | `/v1/api-keys/:id` |
| 認証 | 必須 (`X-API-Key` ヘッダー) |

**パスパラメータ**

| パラメータ | 型 | 説明 |
|---|---|---|
| `id` | UUID | 削除対象のAPIキーID |

**レスポンス: 204 No Content**

**エラーレスポンス**

| ステータス | 条件 |
|---|---|
| 400 Bad Request | `id` が UUID として不正 |
| 401 Unauthorized | `X-API-Key` が未設定または無効 |

## 4. ミドルウェア仕様

**対象ルート:** `/v1/api-keys/:id`、`/v1/users`、`/v1/todos` 配下のすべてのルート

**処理順序:**

1. `X-API-Key` ヘッダーの存在確認（なければ 401）
2. ローカルキャッシュから rawKey で検索
3. キャッシュヒット時 → 4 へ進む
4. キャッシュミス時 → rawKey を SHA-256 でハッシュ化 → DB の `FindByKeyHash` で検索 → キャッシュに保存
5. 認証成功 → `gin.Context` に `user_id` をセット
6. `Next()` を呼び出して後続ハンドラーへ

**コンテキストキー:** `"user_id"` で string 型の UUID が格納される。

---

## 5. データモデル

### APIKey エンティティ

| フィールド | 型 | 説明 |
|---|---|---|
| `id` | UUID | APIキーの識別子 |
| `user_id` | UUID | 発行対象ユーザーの識別子 |
| `key_hash` | string | SHA-256 ハッシュ値（平文は保存しない） |
| `name` | string | APIキーの識別名（用途等） |
| `created_at` | time.Time | 発行日時 |

### キーフォーマット

```
todo_<64文字の hex 文字列>
```

- 内部: `crypto/rand` で 32 バイト生成 → hex エンコード（64文字）
- プレフィックス `todo_` を付与して返却（全体で69文字）
- ハッシュ: `SHA-256(rawKey)` を hex エンコードして保存

---

## 6. セキュリティ仕様

| 要件 | 実装 |
|---|---|
| 平文キーの非保存 | DB には SHA-256 ハッシュのみ保存 |
| 一度限りの返却 | 発行時のみ平文を返し、以後取得不可 |
| ランダム性 | `crypto/rand` による暗号論的乱数生成 |
| 通信経路 | HTTPS を前提（プレフィックスによる識別を推奨） |

**注意事項:**
- 発行時に返却した `key` を紛失した場合、再取得は不可。新たなキーを発行して旧キーを削除する。
- API キーには有効期限が設定されていないため、不要になったキーは速やかに削除すること。

---

## 7. キャッシュ戦略

| 項目 | 値 |
|---|---|
| 実装 | ローカルメモリキャッシュ（`go-cache`） |
| キャッシュキー | rawKey（平文キー文字列） |
| TTL | 5分 |
| クリーンアップ間隔 | 10分 |

**キャッシュ更新タイミング:**
- セット: 認証ミドルウェアの DB 検索成功時
- 削除: API キー削除エンドポイント呼び出し時

> ローカルキャッシュのためサーバーを複数台構成する場合は、キャッシュの一貫性に注意が必要。

---

## 8. エラーレスポンス一覧

| HTTP ステータス | Result Code | 発生条件 |
|---|---|---|
| 400 Bad Request | 4001 | リクエストパラメータのバリデーション失敗 |
| 401 Unauthorized | 4002 | `X-API-Key` ヘッダー未設定、またはキーが無効 |

エラーレスポンスのボディ形式は共通ハンドラーに従う。
