# コーディング規約

## 1. 基本方針

本プロジェクトのコードは、可読性、保守性、一貫性を重視する。Goコミュニティの標準的な慣習に可能な限り従うことを基本方針とする。

## 2. フォーマット

- 全ての `.go` ファイルは、コミット前に `gofmt` または `goimports` を用いてフォーマットされていることを必須とする。
- 多くのエディタでは保存時に自動でフォーマットする設定が可能であり、その利用を強く推奨する。

## 3. 静的解析

- コードの品質を客観的に担保するため、`golangci-lint` を使用した静的解析を行う。
- コミット前やCIでの実行を推奨する。設定ファイルはプロジェクトルートの `.golangci.yaml` に従う。

## 4. 命名規則

- [Effective Go](https://go.dev/doc/effective_go#names) に記述されている命名規則に従う。
- **変数名**: `mixedCaps` を使用する。
- **定数・関数・型名**: 公開（Export）するものは `MixedCaps`、非公開（unexport）なものは `mixedCaps` を使用する。
- **パッケージ名**: 短く、簡潔で、意味のわかる小文字の名前を付ける。スネークケース (`snake_case`) やケバブケース (`kebab-case`) は使用しない。
- **インターフェース名**: Goの慣習に従い、名前に `I` などのプレフィックスは付けない。多くの場合、メソッド名に `-er` を付けた名前が適切である (例: `Reader`, `Writer`, `Formatter`)。

## 5. コメント

- [Effective Go](https://go.dev/doc/effective_go#commentary) に記述されているコメントの慣習に従う。
- **公開される要素**: パッケージ外に公開されるすべてのトップレベルの型、定数、変数、関数には、その目的と利用方法を説明するコメントを記述する。これにより `godoc` でドキュメントが自動生成される。
- **実装コメント**: 複雑なアルゴリズムや、一読して意図が分かりにくい処理については、その処理が「何をしているか(what)」ではなく、「なぜそうなっているか(why)」を説明するコメントを適宜追加する。

## 6. エラーハンドリング

- エラーは決して無視しない (`_` でのエラー破棄は、意図が明確な場合に限定する)。
- 呼び出し元でエラーに関する情報が必要な場合、エラーをラップしてコンテキストを追加することを推奨する。その際は `fmt.Errorf` と `%w` を用いる。
  ```go
  if err != nil {
      return fmt.Errorf("failed to find todo by id %d: %w", id, err)
  }
  ```
- エラーが呼び出し元で回復不可能であり、アプリケーションとして処理を中断すべき場合は、ログに記録した上で適切に処理を終了する。

## 7. パッケージ構成

- パッケージ間の依存関係は、クリーンアーキテクチャの原則に従い、一方向（外側のレイヤーから内側のレイヤーへ）を維持する。
  - `presentation` -> `usecase` -> `domain`
- パッケージ間の循環参照は、コンパイルエラーとなるため、発生させてはならない。設計段階で循環参照が起きないように考慮する。
