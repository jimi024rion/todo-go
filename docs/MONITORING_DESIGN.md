# 監視設計書

## 1. 目的

本ドキュメントは、Todo APIサーバーおよび関連インフラの健全性を継続的に監視するための設計を定める。監視の主な目的は以下の通り。

- **障害検知**: システムの障害やサービス停止を迅速に検知し、対応を開始する。
- **パフォーマンス劣化の把握**: 応答時間の悪化やリソースの逼迫など、パフォーマンスの問題を早期に発見する。
- **キャパシティプランニング**: リソース使用率の傾向を分析し、将来的なリソース増強計画の参考にする。

## 2. 使用ツール

- **監視プラットフォーム**: [Google Cloud Monitoring](https://cloud.google.com/monitoring)
- **ログ収集・分析**: [Google Cloud Logging](https://cloud.google.com/logging)
- **アラート通知**: Google Cloud Monitoring の通知チャネル機能（Slack, PagerDuty, Eメールなど）

## 3. メトリクス監視

Google Cloud Monitoringを利用して、以下のメトリクスを収集・可視化し、異常値を検知した際にアラートを発報する。

### 3.1. インフラストラクチャメトリクス (GCP標準)

Cloud RunやCloud SQLなどのGCPマネージドサービスでは、多くのメトリクスが標準で収集される。

| 対象サービス | メトリクス名           | 説明                               | アラート条件（例）                               |
| :----------- | :--------------------- | :--------------------------------- | :----------------------------------------------- |
| **Cloud Run**  | `CPU Utilization`      | コンテナのCPU使用率                | 5分間継続して80%を超える                         |
|              | `Memory Utilization`   | コンテナのメモリ使用率             | 5分間継続して85%を超える                         |
|              | `Container count`      | 実行中のコンテナインスタンス数     | （傾向監視）                                     |
| **Cloud SQL**  | `CPU Utilization`      | DBインスタンスのCPU使用率          | 15分間継続して80%を超える                        |
|              | `Memory Utilization`   | DBインスタンスのメモリ使用率       | 15分間継続して90%を超える                        |
|              | `Database connections` | アクティブなデータベース接続数     | 上限値の90%を超える                              |
|              | `Storage utilization`  | ストレージ使用率                   | 85%を超える                                      |

### 3.2. アプリケーションメトリクス (SLI/SLO)

ロードバランサのメトリクスやログベースメトリクスを用いて、アプリケーションのサービスレベル指標（SLI）を監視する。

| SLI（指標）          | 計測方法                                   | SLO（目標）         | アラート条件（例）                               |
| :------------------- | :----------------------------------------- | :------------------ | :----------------------------------------------- |
| **Availability**     | 成功リクエスト数 / 全リクエスト数 (5xx系エラーでない) | 99.5% (月間)        | 5分間のエラーレートが2%を超える                  |
| **Latency**          | 95パーセンタイルのレスポンス時間             | 500ms 以下          | 10分間継続して95パーセンタイルレイテンシが1秒を超える |

## 4. ログ監視

「ログ設計書」で定義した構造化ログをCloud Loggingで収集し、特定のパターンに基づいてアラートを設定する。

### 4.1. ログベースアラート

- **対象**: `ERROR`レベルのログ
- **アラート条件**: `level`フィールドが`ERROR`のログが、1分あたり5件以上記録された場合。
- **目的**: アプリケーションコード内で捕捉された予期せぬエラーの発生を迅速に検知する。

- **対象**: パニックログ
- **アラート条件**: `panic`を含むログメッセージが記録された場合。
- **目的**: Goアプリケーションのクラッシュにつながる重大なエラーを即時に検知する。

## 5. ダッシュボード

Cloud Monitoringのダッシュボード機能を用いて、以下の情報を一覧できるカスタムダッシュボードを作成する。

- **主要SLI**: 可用性、レイテンシ
- **リクエスト数とエラーレート**
- **Cloud RunのCPU/メモリ使用率とインスタンス数**
- **Cloud SQLのCPU/メモリ使用率と接続数**

## 6. アラート通知

設定したアラート条件に合致した場合、以下のチャネルに通知を行う。

- **緊急度: 高** (サービス停止に繋がるもの: 5xxエラーレート急増、DB接続断など)
    - **通知先**: PagerDuty, Slackの障害対応チャンネル
- **緊急度: 中** (ただちにサービス停止には至らないが注意が必要なもの: CPU高負荷、ディスク容量逼迫など)
    - **通知先**: Slackの開発者チャンネル, Eメール
