# セキュリティ設計書

## 1. 目的と基本方針

本ドキュメントは、Todo APIサーバーにおけるセキュリティ上の脅威を洗い出し、それらに対する具体的な対策と設計方針を定める。
「セキュアバイデザイン」の考え方に基づき、設計段階からセキュリティを考慮に入れることで、堅牢なアプリケーションを構築することを目的とする。

## 2. 脆弱性対策

OWASP Top 10などを参考に、主要な脆弱性に対する対策を講じる。

### 2.1. SQLインジェクション

- **脅威**: 不正なSQLが実行され、データベースの情報が漏洩・改ざん・破壊される。
- **対策**:
    - ORM (Bob) またはSQLドライバのプリペアドステートメント（プレースホルダ）を全面的に使用する。
    - ユーザーからの入力をSQL文として直接組み立てることは一切行わない。

### 2.2. クロスサイトスクリプティング (XSS)

- **脅威**: APIから返却された値にスクリプトが含まれていた場合、クライアント側で実行されてしまう。
- **対策**:
    - 本APIサーバーはJSON形式でデータを返却するため、直接的なHTMLのレンダリングは行わない。
    - Content-Typeヘッダーに `application/json` を明示的に指定し、ブラウザにHTMLとして解釈されるのを防ぐ。
    - クライアント（フロントエンド）側で、APIから受け取った値をDOMに展開する際には、適切なエスケープ処理を施すことを必須とする。

### 2.3. 安全でないコンポーネントの使用

- **脅威**: 利用しているサードパーティライブラリに既知の脆弱性が存在し、攻撃の足がかりにされる。
- **対策**:
    - GitHubの `Dependabot` を有効化し、依存ライブラリの脆弱性を継続的にスキャンする。
    - 脆弱性が発見された場合は、速やかにライブラリのバージョンアップまたは代替ライブラリへの移行を検討・実施する。

## 3. 認証・認可 (将来的な設計方針)

現状のAPIは認証・認可機能を持たないが、将来的にマルチユーザー対応する際は、以下の設計を導入する。

### 3.1. 認証

- **方針**: JWT (JSON Web Token) を用いたステートレスなトークンベース認証を採用する。
- **フロー**:
    1.  ユーザーIDとパスワードで認証するログインAPI (`POST /auth/login`) を設ける。
    2.  認証成功時、ユーザーIDなどを含むペイロードと有効期限を持つJWTを生成し、クライアントに返却する。
    3.  クライアントは以降のリクエストで、`Authorization: Bearer <token>` ヘッダーにJWTを含めて送信する。
    4.  サーバーはGinのミドルウェアでJWTを検証し、不正なトークンの場合は `401 Unauthorized` を返す。

### 3.2. 認可

- **方針**: リソースへのアクセス時に所有権を確認する。
- **フロー**:
    - `Todo` の更新・削除・個別取得などのリクエストを受けた際、JWTから取得したユーザーIDと、対象となるTodoアイテムの所有者IDが一致するかをUsecase層で検証する。
    - 一致しない場合は、リソースが存在しないかのように見せるため `404 Not Found` を返す。

## 4. 通信の暗号化

- **方針**: クライアントとサーバー間の通信は全てTLS (Transport Layer Security) で暗号化する。
- **対策**:
    - 本番環境では、GCPのロードバランサなどでSSL終端を行い、HTTPS通信を強制する。
    - HSTS (HTTP Strict Transport Security) ヘッダーの利用を推奨し、ブラウザにHTTPSでの接続を強制させる。

## 5. エラーハンドリングと情報漏洩対策

- **方針**: 詳細なエラー情報をクライアントに漏洩させない。
- **対策**:
    - `500 Internal Server Error` が発生した場合でも、スタックトレースやデータベースのエラーメッセージなどをレスポンスに含めない。
    - 詳細なエラー情報はサーバー側のログ（「ログ設計書」参照）にのみ記録し、クライアントには「内部サーバーエラーが発生しました」のような汎用的なメッセージを返す。
