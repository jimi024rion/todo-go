# テスト計画書

## 1. 目的

本ドキュメントは、Todo APIサーバーの品質を保証するためのテストに関する全体的な計画を定める。テストを通じて、以下の項目を達成することを目的とする。

- 各機能が要件通りに動作することの確認。
- コードの変更が既存機能に悪影響を与えていないこと（リグレッション）の防止。
- コードの品質と保守性を高い水準で維持すること。

## 2. テスト範囲

### 2.1. テスト対象

- `internal`ディレクトリ配下に実装される全てのビジネスロジックおよびデータアクセス処理。
- `presentation`層のハンドラおよびAPIエンドポイント。

### 2.2. テスト対象外

- Go言語の標準ライブラリ、および利用するサードパーティライブラリ自体の動作。
- フロントエンドアプリケーション。（本計画書のスコープ外）

## 3. テストの種類と方針

本プロジェクトでは、以下の3種類のテストを段階的に定義・実施する。

### 3.1. 単体テスト (Unit Test)

- **目的**: パッケージやコンポーネントといった単一の単位が、仕様通りに正しく動作することを確認する。
- **対象**: `usecase`, `repository` (モック使用), `domain`内のロジックなど。
- **方針**:
    - 外部依存（データベース、他コンポーネント）はモックに置き換える。Goのインターフェースを活用し、テスト用のモックを注入する。
    - Go標準の`testing`パッケージを使用する。
- **実行コマンド**: `make test` または `go test ./...`

### 3.2. 結合テスト (Integration Test)

- **目的**: 複数のコンポーネントを組み合わせた状態で、期待通りに連携して動作することを確認する。特に、データベースとの連携を重視する。
- **対象**: APIサーバーとデータベースを実際に接続した状態でのAPIエンドポイントの動作。
- **方針**:
    - `testcontainers-go`ライブラリを利用し、テスト実行時にDockerで一時的なPostgreSQLコンテナを起動する。
    - テスト用のデータベースに対して、実際のHTTPリクエストを生成・送信し、レスポンスとDBの状態を検証する。
    - 各テストは独立させ、他のテストに影響を与えないようにする（テストごとにデータをクリーンアップする）。
- **実行コマンド**: `make test-integration` (※Makefileへの追加を想定)

### 3.3. E2Eテスト (End-to-End Test)

- **目的**: 実際のユーザーと同様の操作を行い、システム全体が正常に動作することを確認する。
- **方針**: フロントエンドが実装された後、別途計画する。本計画書のスコープ外とする。

## 4. テストカバレッジ

- **目標値**: 単体テストにおけるテストカバレッジは **80%以上** を目標とする。
- **測定方法**: `go test -cover`コマンドを用いて測定する。

## 5. テスト実行環境

- **ローカル環境**: 開発者がコードを修正した際に、いつでも手元でテストを実行できる。
- **CI環境**: GitHub ActionsなどのCI/CDパイプラインにテスト実行を組み込み、プルリクエストやマージのたびに自動でテストを実行する。これにより、リグレッションを早期に検知する。
